# Messenger Source Interface for Stovo Intelligence

## Feature plan

**User problem.** Stovo Intelligence needs a narrow, authenticated way to consume Messenger resources without database credentials or direct table access.

**Scope.** Add a disabled-by-default service interface for bounded event replay, exact-revision snapshots, current bulk authorization, and exact-revision citation resolution. Create distinct Intelligence installation and connection identities with explicit tenant-to-Messenger-family and connection-to-resource-scope mappings; never alias family or MCP connector IDs. Each installation has an independent default-off enablement. Initially index only server-readable plaintext text messages; E2E-encrypted messages are excluded from snapshots, citations, and the indexable event/revision journal. Do not implement Intelligence-side behavior or modify its repository.

**Observable behavior.** An authenticated, explicitly enabled installation can read only its explicitly mapped tenant and connection; receive ordered, replayable source events for supported plaintext message resources; retrieve content and metadata from one immutable revision; receive current decisions for `read`, `process`, `external_transfer`, and `export`; and resolve citations only against their cited revision. E2E-encrypted messages never enter the indexable source journal. Invalid identity and unavailable policy/storage fail closed. Disabled or unmapped installations cannot read data.

**Constraints and design decisions.** Use an application service and persistence port, not SQL exposure. Use an installation-specific credential and mapping; do not treat an MCP connector token as an Intelligence credential. `tenant_id` is an Intelligence identity stored explicitly and linked to a Messenger family only through a provisioning mapping; a connection separately scopes allowed chats and a server-mapped active Messenger principal. Cursor is opaque, signed, connection scoped, time limited, and carries a commit-ordered stream position. Event delivery is at least once; consumers deduplicate by stable event ID and recover expired cursors by a full backfill followed by a newly issued cursor. Tombstones remain durable for the supported replay window. Snapshot and citation reads require current authorization independently of historical ACL state. `process` may only be allowed when current AI Notes policy allows it; no current Messenger permission exists for external model transfer or agent export, so those operations fail closed until an explicit policy is established. Audit records exclude content, credentials, and locator text. All new installation and connection records default disabled; no real installation is enabled by this change.

## Test plan

All tests use synthetic fixtures and in-memory/fake ports or disposable local test infrastructure; never connect to a live Messenger or Intelligence service.

| Tenant or connection substitution | No cross-scope events, snapshots, decisions, or citations | HTTP contract/security |
| Disabled installation | All source routes are unavailable without storage reads | HTTP contract |

## Discovered Messenger semantics

- **Authorization and tenancy:** `families` own `chats`; `chats.family_id` is the current tenant-like boundary. The authenticated user is resolved by the existing bearer/JWT middleware. MCP connectors are separately token-hash authenticated and map to a family, actor user, enabled/revoked state, and allowed chats (`backend/internal/features/mcp/connectors.go`, `backend/internal/transport/mcp`, `backend/ent/schema/mcp_connector.go`). There is no Intelligence installation or principal mapping and no installation-level opt-in. Chat membership is the current `chat_members` row set; deleting a member row loses history. Connector permissions are not a general AI-processing, external-transfer, or export policy.
- **Event order and replay:** device sync reads immutable `sync_events` by ascending per-family identity `sequence`, filters by family or recipient audience, and returns a signed base64/HMAC cursor bound to family and user (`backend/internal/features/sync/pagination.go`, `backend/internal/adapters/syncstore/postgres_store.go`). Page size is 1–500 (default 100). Existing cursors have no expiry/version and are not connection scoped. An identity sequence orders allocated values, but the implementation does not establish commit order under concurrent transactions. There is no declared retention or full-backfill recovery contract. `outbox_events` is a leased at-least-once async-work queue, not a replay log; its sync-event FK can be nulled and publication state is mutable.
- **Lifecycle and membership history:** REST message creation writes a `message.created` sync event and outbox record in the same transaction. Some file create/validation/deletion paths do likewise. Message edit and delete paths update the row or insert a per-user deletion but do not consistently write source-grade events. File and message `deleted_at` are soft-delete state, not a shared durable resource tombstone. No restore event path or immutable message/content revision history was found. `chat_members` stores current membership plus creation time only; add/remove history and historical ACL evidence are unavailable.
- **Revision and snapshots:** messages have stable IDs and mutable `updated_at`, content/ciphertext fields, and soft deletion. There is no immutable revision ID or content history. Files have lifecycle/object revision fields, but these do not establish a consistent resource revision across content and metadata. A current row read cannot satisfy an exact historical `ResourceSnapshot` or citation lookup.
- **Shared v1 schemas:** `SourceEvent` requires tenant, connection, stable resource/revision IDs, order token, event kind and observation time; source sequence is optional and positive for source events; `tombstone` is available. `ResourceSnapshot` requires unified, content, and metadata revision IDs, content and metadata. `AuthorizationDecision` defines four operations but does not identify the principal or connection. `TextLocator` specifies half-open Unicode code-point offsets into a canonical block. The shared schemas do not define endpoint request/response envelopes, bulk authorization request identity, cursor format/errors, or citation resolution response semantics. Intelligence's README explicitly says exact immutable revision evidence does not prove current permission and requires fresh authorization for citation release.

## Messenger API and versioned contract proposal

Base path: `/api/v1/intelligence/source`. All routes require HTTPS and a dedicated per-connection bearer service credential whose hash is stored in Messenger. Credential verification resolves installation, explicit Intelligence tenant ID, connection, mapped Messenger family, allowed chat scope, and active principal server-side. Caller-supplied tenant, installation, connection, or principal identifiers are never authoritative. Both installation and connection default disabled; the parent config gate also defaults off. Invalid credentials return 401; valid but disabled/unmapped scope returns 403; unknown/out-of-scope resources use indistinguishable 404 responses; malformed input returns 400; exhausted limits return 429; unavailable policy or storage returns 503 with no data or allow decision. Responses carry `Cache-Control: no-store`. Request bodies are capped at 256 KiB, event limits are 1–200, authorization batches are 1–100 resources, per-request timeout is 5 seconds, and per-install rate limit is 60 requests/minute. Audit records include installation, connection, route, and result. Caller-controlled request IDs are not logged.

- `GET /events?cursor=<opaque>&limit=<1..200>` returns `{events: SourceEvent[], next_cursor: string, has_more: boolean}`. In the current implementation, omitting cursor starts at sequence zero and only returns events captured after the connection was enabled; it does **not** seed existing messages. Cursor is authenticated, opaque, connection-scoped, and expires after 7 days. Event ordering is intended to be a per-connection transactional order token; consumers deduplicate by `event_id`. Expired cursor returns 410 `cursor_expired` with `recovery: full_backfill_required`, but no full-backfill/fence endpoint exists yet, so that response is a proposal and cannot currently be acted on. Thirty-day event/tombstone retention is also proposed, not enforced.
- `GET /resources/{resource_id}/snapshot?revision_id=<id>` returns one `ResourceSnapshot` for that exact revision or 404. Text messages stored as `legacy_plaintext` or `server_at_rest` are eligible; server-at-rest ciphertext is decrypted only inside Messenger after current authorization. `end_to_end` messages are excluded from source revisions, snapshots, citations, and indexable events. Content and metadata are read from one immutable revision record; missing revision returns 404, never a substitute current revision.
- `POST /authorization:check` accepts `{resource_ids: string[], operation: AuthorizationOperation}`. The principal is connection-mapped, not accepted from the request. Returns `{decisions: AuthorizationDecision[]}` in request order. `read` uses current family activity and chat membership; `process` additionally requires current family AI Notes enablement. `external_transfer` and `export` return denied because Messenger has no matching current policy. Unknown/out-of-scope resources and policy failures cannot produce `allowed: true`; policy/storage failure returns 503 for the batch.
- `POST /citations:resolve` accepts `{resource_id, revision_id, locator}` where locator validates against the shared locator union, initially `TextLocator`. It supports plaintext message revisions only and returns `{source_reference, revision_id, excerpt}` only for an exact retained revision and valid half-open Unicode code-point bounds, after a fresh current `read` check; otherwise returns 404. Locator text is never logged. **The v1 schemas do not define `source_reference` or citation response shape; this shape is a Messenger-side proposal pending shared adoption.**

## Contract gaps and required versioned changes

1. Messenger cannot currently produce exact historical content and metadata revisions, complete lifecycle events, durable source tombstones, or membership history. A source-specific append-only revision/event store and transactionally ordered per-connection position are required; existing device sync sequence and outbox are insufficient. Source capture must exclude E2E-encrypted messages and must not imply decryption. The adapter's supported-resource profile will be plaintext text messages only; other resources require a later explicit contract profile.
2. Existing families, MCP connectors, and actor users do not define the Intelligence concepts `tenant`, `installation`, `connection`, and scoped service principal. Add explicit installation/connection enrollment and per-install enablement; do not alias these concepts silently.
3. `AuthorizationDecision` omits principal and connection identity, policy evaluation time semantics, and revocation freshness. Propose v2 decision fields `connection_id`, `principal_id`, and `membership_revision` (or a policy epoch) plus a defined maximum revocation propagation interval. The bulk request schema carries operation and resources while principal remains credential-mapped. Messenger has no general current policy for external model transfer or agent export; these decisions remain denied until Messenger adopts explicit policy semantics.
4. `ResourceSnapshot` has no explicit deleted state, source type, or locator/source-reference mapping. `TextLocator` is only a locator shape and `SourceEvent` has no resource type. Propose versioned schemas for a resource-kind discriminator and citation source reference, plus explicit deleted/tombstone snapshot behavior.
5. Shared v1 lacks event page, cursor expiry/backfill, authentication, error, rate-limit, and citation-resolution request/response schemas. Publish these before calling this adapter v1-conformant. A versioned amendment is needed if v1 consumers assume stronger sequence/retention or principal semantics than their schemas state.

## Proposed Stovo Intelligence contract v2 amendment

This is a proposal for the Intelligence contract owners; no files in the Intelligence repository were changed and none of these additions should be treated as accepted v1 behavior.

1. **Decision identity and freshness:** add required `connection_id`, `principal_id`, and `policy_revision` to authorization requests and decisions; add `decided_at` plus a documented `max_staleness_seconds`. Messenger binds principal and connection from the credential and evaluates each request against current membership. A cached decision older than the freshness bound is unusable. Keep the v1 four operation values; Messenger denies `external_transfer` and `export` until it has corresponding explicit policy.
2. **Event pages and cursor recovery:** standardize `SourceEventPage` as `{events, next_cursor, has_more}` and define cursor as an opaque string scoped to one connection and tenant. Require transactional commit ordering, at-least-once delivery, stable event IDs for deduplication, and a 410 `cursor_expired` response with `recovery: full_backfill_required`. Define a recovery sequence: obtain a snapshot/backfill fence, enumerate the full supported source scope, then resume events strictly after that fence. State retention and maximum revocation propagation as negotiated server capabilities rather than unstated assumptions.
3. **Citation resolution:** add request schema `{tenant_id, connection_id, resource_id, revision_id, locator}` while treating IDs in the request as selectors only; the authenticated connection remains authoritative. Define response `{source_reference, revision_id, excerpt}` and require exact revision match, half-open Unicode code-point offsets into a named canonical text block, and fresh `read` authorization before returning any excerpt. Define not-found behavior for stale, deleted, out-of-scope, or unsupported locators.
4. **Resource profile and encrypted content:** add a `resource_kind` discriminator and a declared source capability profile. For this Messenger profile, include only text messages whose content is server-readable (`legacy_plaintext` or Messenger-decryptable `server_at_rest`). Do not transmit `end_to_end` ciphertext as text or create indexable revisions for it. If Intelligence needs to represent unavailable encrypted resources, add an explicit `content_state` enum in a later version rather than overloading empty content.
5. **Tombstones and authorization invalidation:** define delete/restore lifecycle semantics and tombstone retention; define `acl_change` as an invalidation hint that requires a new authorization check, never as a grant. Historical ACL evidence and source events do not establish current access. Define how a move changes container scope and how a consumer removes a resource that has left its connection scope.

## Implementation sequence and rollout gate

### Current implementation status

This change contains a mounted, default-off HTTP API, credential-hash resolver, installation/connection/chat-scope tables, message/member event capture, immutable revision/event rows, cursor signing, current membership/AI Notes checks, snapshot and citation callbacks, per-connection rate limiting, metadata-only audit writes, synthetic HTTP/config tests, and a synthetic PostgreSQL contract test. The PostgreSQL test exercises authentication, initial replay, exact snapshot and citation, current authorization, per-user visibility revocation, E2E transition, membership removal, and audit writes. A regression test also exposed and verifies that audit writes run with a bounded context after request cancellation.

Known contract gaps: there is no seed/backfill/fence workflow for pre-existing resources or cursor expiry, and no defined/verified maximum propagation interval. Membership and per-user message visibility changes emit metadata-only `acl_change` events; those scoped invalidations remain deliverable after chat membership removal, while current `read`/snapshot checks fail closed. Authorization policy revisions incorporate current chat membership, AI Notes state, principal activity, and per-user message visibility. These SQL semantics and migration triggers were exercised against disposable PostgreSQL 17. Thirty-day retention/pruning is not implemented. The migration's immutable delete triggers conflict with connection/installation `ON DELETE CASCADE` cleanup. No enrollment/credential rotation workflow exists. Event completeness outside covered message/member transitions, recovery, retention, and operational lifecycle remain unverified; no tenant should be enabled.

1. Extend synthetic black-box tests to cover backfill, all replay edge cases, and lifecycle boundaries beyond the current PostgreSQL test.
2. Implement safe enrollment/credential rotation and a bounded consistent backfill/fence flow, or keep the feature gate unavailable.
3. Close current-policy, revocation, retention, and cleanup semantics, then verify transactional event capture and exact-revision reads against disposable PostgreSQL.
4. Regenerate and validate the Atlas checksum; run focused backend contract tests, broader `go test ./...`, and `make lint`.
5. Repeat independent adversarial review and only then document rollout prerequisites; do not enable a real tenant as part of this work.

This Messenger repository may implement the agreed side of the proposed contract, but must not change the Intelligence repository or claim unaccepted v2 fields are already shared. The process route is disabled by default; no real tenant may be enabled until installation enrollment, durable revision/event storage, current policy mapping, retention/recovery operations, and shared contract gaps above are resolved and verified.
