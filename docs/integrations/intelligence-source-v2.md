# Messenger Intelligence Source v2 operations

This document describes the Messenger-side v2 boundary implemented for a future, explicitly approved canary. It is not a production enablement request or a claim that the Intelligence consumer is ready.

## Default state and enrollment

Source access stays disabled unless both process gates are enabled:

- `INTELLIGENCE_SOURCE_ENABLED` defaults to `false`.
- `INTELLIGENCE_OIDC_ENABLED` defaults to `false` and is a separate gate.

Keep both false in development, staging, and production until the Intelligence owner has approved the v2 contract and the rollout owner has separately authorized an installation. Enabling these flags alone does not grant a user or client access. The client ID, exact HTTPS callback allow-list, active installation, one-chat connection, and each individual grant are checked separately. Grants (`read`, `process`, `external_transfer`, and `export`) start denied; do not treat chat membership as consent.

## Preparing Messenger credentials

For the blue/green deployment, the OIDC and source environment values below are passed to both backend colors. Caddy routes root OIDC and `/api/v2/intelligence/*` requests to `INTELLIGENCE_BACKEND_UPSTREAM`; by default it follows the configured backend upstreams. For the multi-server deployment, set `INTELLIGENCE_INTEGRATION_TENANT_SLUG` to the one authorized server slug and set `INTELLIGENCE_BACKEND_UPSTREAM=stovo-backend-<slug>:8000` on the gateway. Only the selected tenant receives the integration credentials. The GitOps orchestrator also accepts the tenant and integration settings; its separately managed gateway must route those root endpoints to that same selected tenant. Configure both settings consistently and verify the routes before enabling source access. Other tenant backends receive no integration credentials.

The browser consent ticket uses the configured `APP_URL` path, including `/s/<slug>` for a tenant, and is cleared on the same path after use. The tenant identity remains determined by the selected backend and authenticated session, never by a caller-supplied tenant field.

Run `scripts/generate-messenger-intelligence-secrets.sh` on a trusted operator workstation. Pass the exact `issuer` value advertised by Messenger's `/.well-known/openid-configuration` endpoint, followed by the public HTTPS origin of Intelligence. Both arguments must be HTTPS origins without a path or trailing slash. For example:

```sh
issuer=$(curl -fsS https://messenger.example.com/.well-known/openid-configuration | jq -er '.issuer')
OUT_DIR="$HOME/.config/stovo/messenger-intelligence" \
  scripts/generate-messenger-intelligence-secrets.sh "$issuer" https://intelligence.example.com
```

Replace the example hosts with the deployed hosts. The script creates a random client ID and secret, an RSA private signing key, and a `messenger.env` file. It sets both feature gates to `false`. The output directory is private to the current user; transfer the values to the deployment secret manager and remove local copies when they are no longer needed. Set the contents of `oidc-signing-private.pem` as `INTELLIGENCE_OIDC_SIGNING_PRIVATE_KEY_PEM`; Messenger expects the PEM value, not a file path.

The current Messenger implementation uses the same `INTELLIGENCE_OIDC_CLIENT_ID` and `INTELLIGENCE_OIDC_CLIENT_SECRET` for OIDC and Source consent. It validates both callback URIs from the comma-separated `INTELLIGENCE_OIDC_REDIRECT_URIS` setting. The Intelligence consumer must use credentials compatible with this behavior. If its deployment requires separate OIDC and Source client credentials, stop and reconcile that contract before enabling either gate; this script does not provision a second Messenger client.

`INTELLIGENCE_SOURCE_SECRET_ENCRYPTION_KEYS` belongs to the Intelligence deployment and is not generated by this script. The source bearer credential is issued by Messenger during a user's consent flow; operators should not generate or reuse it manually.

For an explicitly approved pilot, an operator with access to the selected backend container can provision the one enabled installation and the user's stable OIDC subject after migrations are applied and `INTELLIGENCE_OIDC_ISSUER` is configured:

```sh
docker exec <selected-backend-container> intelligence-source-ops enroll \
  --family-id <messenger-family-id> --tenant-id <intelligence-tenant-id> \
  --user-id <active-messenger-user-id>
```

The command uses the backend's configured issuer, validates the active user's family, and returns JSON containing the stable `subject`, `tenant_id`, `principal_id` and `installation_id`. Configure the subject, tenant ID and principal ID in Intelligence's explicit MCP allowlist: the principal ID must equal the selected Messenger user ID because Source v2 binds every result to that identity. Repeating the command for the same binding returns the same values. It rejects conflicting enabled installations and does not create a chat connection or grant any chat access; the user still selects a chat and grants operations in Messenger. Treat the output as identity data, and do not run it on a live tenant before its separate approval and recovery gates.

When a future rollout is approved, provision only operator-controlled configuration. The OIDC settings are `INTELLIGENCE_OIDC_ISSUER`, `INTELLIGENCE_OIDC_CLIENT_ID`, `INTELLIGENCE_OIDC_CLIENT_SECRET`, `INTELLIGENCE_OIDC_REDIRECT_URIS`, `INTELLIGENCE_OIDC_SIGNING_KEY_ID`, `INTELLIGENCE_OIDC_SIGNING_PRIVATE_KEY_PEM`, and optionally `INTELLIGENCE_OIDC_PREVIOUS_SIGNING_KEYS_JSON`. The issuer must be its canonical HTTPS origin and callbacks must be exact registered HTTPS URIs. Keep confidential secrets and private signing keys in the deployment secret manager; do not add them to repository files, tickets, chat, test output, or logs. Use synthetic values and identities for local verification.

OIDC ID tokens, one-use consent codes, and source bearer credentials are separate credentials. Store only the source credential verifier in Messenger; deliver the source credential once to the registered confidential client. Never pass Messenger credentials to Codex or use an ID token as a source credential.

## Signing-key rotation

Use an overlap rotation so already-issued ID tokens remain verifiable:

1. Generate a new RSA signing key outside the repository while leaving the current signer active. Add the new public key and a new unique key ID to `INTELLIGENCE_OIDC_PREVIOUS_SIGNING_KEYS_JSON`, deploy, and confirm the JWKS endpoint advertises both IDs. This setting accepts public PEMs only; it must not contain private-key fields.
2. Switch `INTELLIGENCE_OIDC_SIGNING_KEY_ID` and `INTELLIGENCE_OIDC_SIGNING_PRIVATE_KEY_PEM` to the new key, and replace the previous-key entry with the former signer's public PEM and ID. Confirm the JWKS still advertises both IDs and newly issued ID tokens use the new `kid`.
3. Keep the former public key published until every token signed by it has expired and the relying party has confirmed the overlap. Then remove it from the previous-key list.

If key material, a client secret, or a source credential may have leaked, disable both feature gates while investigating. Rotate the affected key/secret or revoke the affected source connection; do not log or paste the credential during incident handling.

## Schema migration and retention

Apply the backend migrations through the normal deployment migration job. Before rollout, validate the migration set with Atlas and verify `backend/migrations/atlas.sum` is clean. The v2 retention migration adds backup horizons, metadata tombstones, a backup-inventory checkpoint, and restore-gate state. Active payloads do not have a time-based expiry. Source connections are detached from deleted users/installations after retirement so immutable event/revision identities survive account cleanup. Do not manually delete v2 event/revision identities to imitate content deletion.

Active payloads follow the source message lifecycle. Message deletion, chat-scope exit, read-grant revocation, or connection revocation purges the affected payloads transactionally with the invalidation event. An exact read whose payload has been purged returns the same not-found result as an unavailable or out-of-scope revision. Metadata-only events retain stable IDs and revision identity after the tombstone ledger entry is pruned. The 30-day maximum applies to restorable backup copies that may contain source text, not to active Messenger source payloads.

The retention API accepts each restorable database backup's creation time and last-restorable time, plus a complete-inventory checkpoint. This repository currently has no backup-controller call site that registers those values or marks an inventory complete. The backup owner must wire both operations into backup creation and expiry before enabling source access. This repository also has no confirmed off-host backup target or tested five-minute RPO. Until the backup integration and target are verified, do not claim that backup copies expire within 30 days or that a five-minute RPO is met. Tombstone and backup metadata pruning fails closed without a current complete inventory and may grow without bound. When wired, the restorable window is capped at 30 days; the tombstone ledger remains at least 7 additional days beyond the applicable backup horizon and never less than 37 days from tombstone creation. If backup metadata is missing, stale, or inconsistent, do not prune the ledger or begin a restore. Do not extend backup restorability beyond 30 days without changing the contract and its tests first. The DB-only `intelligence-source-ops` CLI supports `backup register` and `inventory verify`; examples are in the [self-hosting guide](../self-hosting/docker-compose.md#intelligence-source-v2-backup-tracking-and-restore-safety). No automated backup controller invokes these operations.

## Restore procedure

Treat any database restore as a source-access outage. `INTELLIGENCE_SOURCE_V2_RESTORE_EPOCH` is deployment state stored outside database backups. Set a new unpredictable epoch in the deployment configuration before each restore; the restored database retains its old epoch, so v2 source routes return unavailable even if the restored row says `blocked=false`. Do not reuse an epoch across database restores.

The current restore gate and tombstone rows are stored in the same Messenger database as source content. A full database rollback can roll them back together, so they cannot independently prove that post-backup tombstones are complete. Accordingly, `BeginIntelligenceSourceV2Restore` blocks source routes and returns unavailable, and `CompleteIntelligenceSourceV2Restore` cannot reopen them. Do not bypass this guard or treat same-database high-water checks as independent evidence.

The operator CLI does not expose restore commands. Before restore can be enabled, the backup/restore owner must provide one of these verified paths: (a) restore a current tombstone journal from independent off-host state and prove its completeness relative to the selected content backup, or (b) keep source routes closed while all affected Intelligence scopes are reset/reindexed from an authoritative current source, including connections that may be absent from the restored Messenger snapshot. The second path also requires the Intelligence owner and is not implemented here. In either case, test the full rollback procedure with disposable backups before adding an integration that can reopen the gate. If the proof source or full scope inventory is missing, leave both feature gates disabled.

The application restore gate denies v2 source routes when its row is missing, marked blocked, or contains an epoch different from deployment state. Cleanup/storage errors are surfaced as unavailable and must not be treated as successful cleanup or restore verification. Preserving support tables from a latest off-host checkpoint may be part of the future restore path, but restoring only the selected database snapshot is insufficient.

## Release and consumer boundary

There is no live canary in this implementation task. Development and verification use synthetic identities/content and disposable local PostgreSQL/Redis only. Do not connect a live tenant, enable an installation, or claim production readiness based on Messenger tests.

Messenger emits durable invalidations, checks current grants on reads, and caps authorization-decision freshness at 300 seconds. This alone does not prove end-to-end suppression. Before any canary, the Intelligence contract owner must agree to and independently verify invalidation consumption, cache/index/export expiry, full-scope reset after cursor expiry, exact-revision citation behavior, and restore replay ordering. Until then, the consumer-side suppression obligation remains unverified and no five-minute end-to-end suppression guarantee may be claimed.

The v2 authorization endpoint evaluates one grant per decision. Before sending a source snippet to Qwen, Intelligence must obtain current allowed decisions for `read`, `process`, and `external_transfer` for that resource. Before returning a source citation through Codex, it must obtain current allowed decisions for `read` and `export`. Citation resolution in Messenger requires `read` because it returns the excerpt to the Intelligence service; that response alone does not authorize export to Codex. Messenger does not implement the Intelligence v2 adapter, OIDC subject allow-list, MCP-token flow, or these downstream composition checks; those require a separate Intelligence-side change and contract tests.
