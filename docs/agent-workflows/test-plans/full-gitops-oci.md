# Stovo multiserver GitOps test plan

Status: draft for combined human review; these are planned checks, not executed results. Applies to `docs/agent-workflows/specs/full-gitops-oci.md`.

Use synthetic secrets and isolated databases, object stores and VM resources. Include multiple registered tenants, a dynamically created tenant, a root-route tenant and a tenant with existing files. Record the Git source SHA, release commit, image digests, VM architecture and component versions with evidence. Never print or persist real secret values in test output.

| Acceptance ID | Test and expected result | Layer |
| --- | --- | --- |
| GITOPS-01 | Passing CI promotes a single atomic release snapshot containing the exact tested SHA, deployment files and image digests; a changed configuration is promoted with its corresponding images. | CI integration |
| GITOPS-01 | Failed, skipped, pending and canceled required checks do not promote; explicitly inapplicable conditional jobs may be skipped only under the approved allowlist; two concurrent runs finishing out of order cannot replace a newer release with an older one; intentional rollback remains held until explicit resume. | CI integration |
| GITOPS-02 | A fresh ARM64 stage host starts Doco-CD, polls only the stage release branch, pulls immutable images and applies the complete Compose configuration with no inbound webhook and no SSH deployment. | Stage end-to-end |
| GITOPS-02 | No config or image change causes no unnecessary recreation; a valid release change converges once. Restart Doco-CD and the VM and verify recovery and repeatability. | Stage integration |
| GITOPS-03 | Existing tenants converge to the selected backend image digest; unchanged healthy tenants are not needlessly recreated; stopped, stale-image and wrong-config cases converge. Unowned containers remain untouched. Running-only tenants block adoption and are preserved until explicitly reconciled. | Controller integration |
| GITOPS-03 | Create, update and delete a tenant through the application before and during rollout; assert correct database, bucket, networks, routing and absence of missed or duplicate workloads. | Stage end-to-end |
| GITOPS-04 | Master migrations and Atlas tenant migrations execute against each intended database in order, without concurrent conflicting runs. Baseline the master migration ledger against an existing schema, simulate crash/lock loss and stale process resumption while a new holder operates, proving fencing of Docker/SQL mutations; verify old/new schema compatibility. New tenants receive the same current migration set. | Database integration |
| GITOPS-04 | Simulate a tenant migration failure and an incompatible rollback; rollout is marked failed, failure is observable and no automatic database rollback or data loss occurs. Retry a recoverable failure. | Stage fault injection |
| GITOPS-05 | The adapter reads a synthetic authorized Vault secret using the actual VM principal and network namespace. Unauthorized OCID, unexpected field and unauthorized client requests are rejected. | OCI stage integration |
| GITOPS-05 | Compare secret delivery with expected runtime behavior without printing values; verify no values in Git, promotion artifacts, logs or errors. Rotate a secret and promote only its version in GitOps; verify all fetched keys belong to that one version and new workloads consume it without an application source commit. Exercise concurrent rotation and app promotion, previous Vault-version availability during rollback, and coordinated PostgreSQL/MinIO, TURN/LiveKit and encryption-key rotation policies. Never rotate persistent-data keys by merely updating a Vault value. | OCI stage integration |
| GITOPS-05 | Private Git/registry bootstrap succeeds using least-privilege credentials; rotation, expiration and revoked credentials yield visible failures without disclosure. | Stage fault injection |
| GITOPS-06 | Simulate unavailable Vault, invalid/missing keys, unavailable Git/registry, no disk space, missing tenant bucket and unhealthy tenant. No new release is reported healthy; running data remains available where possible; retry is observable and bounded. | Stage fault injection |
| GITOPS-06 | Public website, root authentication endpoint, tenant routes, WebSocket, storage/file reads, and representative call endpoints remain correct after deployment. | Stage end-to-end |
| GITOPS-07 | Inspect each selected image manifest for linux/arm64 and run Doco-CD, adapter, orchestrator, frontend, backend, migrations and infrastructure images on actual Ampere ARM64. Record digests and versions. | Manifest + stage smoke |
| GITOPS-08 | Rehearse importing a cloned existing stack with its project name, networks, volumes, Caddy state and multiple populated tenants; prove no duplicate or removed data resources, proxy networks and correct versioned Caddy configuration after release and agent restart. | Stage migration |
| GITOPS-08 | Restore a matching database and object-store backup with its existing encryption key; rehearse failed cutover and a compatible release rollback. Document migrations that prohibit automatic rollback. | Stage disaster recovery |
| GITOPS-09 | Concurrent tenant operations and rollout use the shared database advisory-lock protocol; old/new deployment overlap is prevented; after successful cutover the SSH jobs cannot deploy. Exercise the documented recovery procedure before removing old credentials. | Stage cutover rehearsal |

Before requesting production cutover, attach results for every criterion, exact head and artifact digests, known failures, and a runbook with backup and recovery evidence. Missing ARM64, OCI, registry or staging infrastructure is blocked evidence, not a pass.
